## This repo: fsbhoa_ac_core

The **core WordPress plugin**, plus one Go backend service (`monitor_service`).

## PHP plugin structure

- `fsbhoa-ac-core.php` — entry point; `require_once`s every module explicitly (no autoloader). New files must be added here. Handlers are instantiated in three places: `run_fsbhoa_action_handlers()` on `init` (AJAX/`admin_post_` action classes), `fsbhoa_ac_api_init()` on `rest_api_init` (REST classes call `register_routes()`), and `is_admin()` / front-end blocks.
- `includes/<module>/` — per-feature modules, each typically a `*-admin-page.php` (rendering, often a `WP_List_Table`), a `*-actions.php` (form/AJAX handlers registered in the constructor), and `views/` templates.
- The UI is primarily **front-end pages rendered via shortcodes** (`includes/class-fsbhoa-shortcodes.php`: `[fsbhoa_cardholder_management]`, `[fsbhoa_live_monitor]`, `[fsbhoa_vendor_management]`, etc.), which is why `WP_List_Table` is loaded outside admin. The site forces login for all front-end pages.
- REST routes: `/monitor/*`, `/reports/*`, `/test/*`, `/access/*`, and the vehicle log's `/vehicle-event`, `/vehicle-recent` and `/vehicle-image/{id}` (`includes/monitor/class-fsbhoa-vehicle-log-rest-api.php`).
- JS/CSS per module in `assets/js`, `assets/css`; third-party libs (jQuery UI, DataTables, Chart.js, Croppie, Tailwind) are vendored in `assets/vendor`.
- The nightly rebuild / daily time sync cron hooks are scheduled and handled in `fsbhoa_ac_uhppote`, not core (see ARCHITECTURE.md).

### Schema changes — keep three files in sync
- `includes/class-fsbhoa-core-repository.php` → `create_tables()` (runs on activation; `CREATE TABLE IF NOT EXISTS`)
- `db_schema.sql` — phpMyAdmin dump of the current schema (reference)
- `migration.sql` — script to upgrade the production DB to the new release

## Go monitor service (`monitor_service/`)

WebSocket hub (gorilla/websocket) for the live monitor. Endpoints: `/notify` (events in), `/update-gate-status`, `/ws` (browser clients). Reads `/var/lib/fsbhoa/monitor_service.json` (`-config` flag), which is generated by `includes/admin/class-fsbhoa-ac-settings-page.php`.

## Commands

```bash
./build.sh              # build Go service(s) -> monitor_service/fsbhoa_monitor
./build.sh install      # also install it, and its unit (systemd/), restart if changed
./deploy-production.sh  # deploy all the plugins (~/deploy-production.sh links here)
cd monitor_service && go build ./... && go vet ./...
php -l path/to/file.php # syntax check (no PHPUnit/linters configured)
sudo systemctl status fsbhoa_* --no-pager
```

`TEST_PLAN.md` is a manual test plan, and there is an in-app Test Suite page (`includes/admin/class-fsbhoa-test-suite-*`). 

## Deployment (since 2026-11-15)

- **Each service plugin** (core, kiosk, uhppote, vehicle, zebra) has the same `build.sh`, which runs from any folder: `build.sh` builds; `build.sh install` also installs the binaries in `/usr/local/bin` (keeping the one replaced as `.bak`) and the plugin's units from `systemd/` (`@USER@` becomes the user who runs it, `@PLUGIN_DIR@` the plugin folder; group `www-data`), and restarts only what changed. A service whose config (`/var/lib/fsbhoa/*.json`) is missing isn't started: the settings pages write the configs.
- **`deploy-production.sh`** (here; `~/deploy-production.sh` links to it), run as the service user: clones or pulls (`--ff-only`; `--no-pull` deploys what's checked out) the seven repos into that user's home, links each into WordPress (links, so quick fixes work in place), runs each `build.sh install`, and lists inactive plugins (it never activates one) and the services. While the V1 plugin `fsbhoa-access-control` is active it only builds. It's also the routine update. Needs wp-cli (on production since 2026-11-15: `/usr/local/bin/wp`, 2.12.0).
- **`cutover-v2.sh`** (here): the one-time switch of production from V1 to V2. `check <RAM export CSV>` changes nothing (checks, pull, build); `run <CSV>` backs up to `~/cutover_backup_<time>/` (database, binaries, units, kiosk autostart), then: maintenance mode, stop the services, deactivate V1, `migration.sql`, mark the import plugin's one-time migrations done (so they can't regroup migration.sql's households on the first page load), delete the DoorKing proxy's options, `FSBHOA_AC_ENVIRONMENT` = production, link and activate the V2 plugins, write the service configs from the settings (as www-data), `deploy-production.sh --no-pull`, the DoorKing import (`fsbhoa_ac_doorking/tools/cli_import.php`: dry run, residents, vendors), the OFFICE listing, the kiosk autostart; and prints the steps left by hand (`CHECKLIST.txt`). `rollback <backup folder>` puts V1 and its database back. `--rehearsal` allows the testbed; `--yes` skips the confirmations. Rehearsed on the testbed 2026-11-15 (V1 plugin from `fsbhoa_v1_backport` and production's ac_* tables loaded first): run, rollback, run again; the same results as the rehearsal re-run (dry run skip 106, conflict 124, former 7, current 2; 513 residents and 46 vendors imported; OFFICE got 9925), and the rollback dropped only the six new tables. With `--rehearsal` the backup leaves out `ac_vehicle_log` (gigabytes of photos on the testbed; the cutover doesn't change it). The kiosk service restarts a few times while maintenance mode is on (it gets WordPress's maintenance page) and settles when it ends.
