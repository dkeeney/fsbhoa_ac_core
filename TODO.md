## Schema

- [ ] **4. Make `ac_credentials.expiration_date` a `DATE`, not a `DATETIME`.** Expiry is a calendar date. Storing a time makes every value come back as `2099-12-31 00:00:00`, so code that compares it with `'2099-12-31'` ("never expires") silently fails. `fsbhoa_ac_zebra` hit this and printed "Expires: 12/31/2099" until it was changed to compare only the date part.
  - Change the column in `db_schema.sql`, the `CREATE TABLE` in `includes/class-fsbhoa-core-repository.php`, and add an `ALTER TABLE ... MODIFY expiration_date DATE DEFAULT NULL` step to `migration.sql`. MySQL drops the time when converting, so existing values like `2099-12-31 23:59:59` (from the old `COALESCE` in `migration.sql`) become `2099-12-31`.
  - Decide whether a badge is valid *through* its expiry date. Core's access log (`fsbhoa-access-service-functions.php`, `strtotime($cred->expiration_date) < $now`) treats a bare date as midnight at the start of that day, so the badge would count as expired for the whole of its last day. The UHPPOTE controllers treat their end date as inclusive.
  - Then check the code that reads the column, so nothing relies on the time part: `fsbhoa_ac_uhppote` (credentials, RFID section, permission compiler, bulk sync), `fsbhoa_ac_kiosk` (admin override, REST API), `fsbhoa_ac_doorking` (rotation, vendor importer) and `fsbhoa_ac_zebra` (print actions, badge preview). Most already take `substr(..., 0, 10)` or write a bare date, so the change should be safe, but test the badge edit screen, the permission compile and a print.

## Time

- [x] **6. Review the remaining `date()` and `strtotime()` calls for UTC.** WordPress runs PHP in UTC, so these work in UTC unless given a time zone (convention: `other_docs/ARCHITECTURE.md`, "Local time everywhere"). Done 2026-10-14 for the access-control plugins (core, uhppote, DoorKing, import, Zebra, vehicle, kiosk). Every call was read:
  - **Fixed:** a plain `date()` for "now" works in UTC, so after 17:00 local (16:00 in winter) it gave tomorrow. That broke the reports' default month and year (`get_usage_analytics_callback`, `get_daily_summary_callback`, the analytics page's selected month and year) and the date in the CSV export file names (access log, cardholders). The card lookup's "expired" note compared a local date with a local timestamp correctly, but marked a card expired on its last valid day; it now uses the kiosk's rule (valid through the expiry date, compared as `Y-m-d` strings with `current_time( 'Y-m-d' )`). uhppote's Contractor expiry check compared a date's UTC midnight with `time()`, so from 17:00 it refused tomorrow's date. The import status showed UTC times (`wp_date()` now). DoorKing's vendor-code settings named the wrong previous month on the 31st (`-1 month` from October 31 is October 1); not a time zone bug, found on the way.
  - **Harmless, left as they are:** `date( fmt, strtotime( $local_string ) )` only reformats a local time (both halves work in UTC), `date()` of `current_time( 'timestamp' )` gives local time, and `date( 'F', mktime( 0, 0, 0, $m, 10 ) )` gives a month name. MySQL runs in the system time zone (local), so the `NOW()` comparisons with local `event_timestamp` values are right.
  - **Still to do:** `fsbhoa_website_user_sender` schedules its daily sync at `time()` (13:40 local). Change it only when it can be tested in production, since it pushes real logins to the website. The lighting, intrusion and vendor-code receiver plugins weren't reviewed.
